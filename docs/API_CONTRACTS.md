# OptionsPilot V0.8 API Contracts

V0.8 adds `/api/v1` as the canonical application transport. Existing `/api`
routes remain compatibility aliases and retain their historical raw payload
shapes while the shipped browser client migrates.

## REST

Versioned success responses use `{data, meta}`. Errors use `{error, meta}` with
a stable `error.code`, human-readable message, optional details, API version,
and request ID. Request IDs are accepted through `X-Request-ID` or generated by
the server.

The v1 surface currently covers status, workspace, runtime, notifications,
health, host/capabilities, sync metadata, updates, guide, market data, and
intelligence summary. Additional routes should call an existing
application/service method rather than copy a legacy handler.

## WebSocket

`/api/v1/ws` emits versioned envelopes with `version`, `type`, `message_id`,
`timestamp`, `data`, and `meta`. It begins with `hello.accepted`, then emits
`status.snapshot` or `status.heartbeat`. `/ws` remains the legacy raw protocol.

## Client context

Client identity and requested capabilities are transport metadata. The
application receives `RequestContext`; it does not inspect FastAPI requests or
WebSocket objects. Authentication is currently anonymous loopback access, with
an explicit `AuthProvider` boundary reserved for paired device tokens.

## Compatibility

New fields are additive. A future client must ignore fields it does not know.
Legacy aliases are not allowed to call a second implementation of business
logic.
